# Templating

Each section can be (partially) generated by using jinja2 templating strings
(j2-strings), so every string in the specs YAML will be rendered and the result
replaces that j2-string (so you can generate all data types with your j2-string,
not only strings).

This applies uniformly across the file: every string value — including
deeply nested ones inside `repo` (plugin/connection/details),
`types[].actions[].details`, `types[].logs[].details` and
`types[].links[].url` — is rendered
as a j2-string. There is no separate "format-string" syntax for any
field. The only exceptions are the `auth.oidc.jwt.*` and
`auth.oidc.access_tokens.jwt.*` claim mappings (see
[`auth`](file/auth.md)), which are intentionally Python
`str.format` patterns over the validated token claims, and the
`description` of subschemas in the [`schema`](file/schema.md) (only the
top-level `description` is rendered).

{: .important}
Undefined variables and attributes are **errors** (Jinja2 `StrictUndefined`),
so use `| default(...)` for everything that may be missing (e.g.
`new.data.blub | default('')`). A failing j2-string in `schema` or `types`
fails the request, in `roles` or `sets` it makes the role/set not match (and
logs an error), and in `repo` or `auth` it stops YAC at startup.

{: .warning}
The specs file is **first** parsed as a YAML file, so no matter what you do
within your j2-strings, the file must be valid YAML.

Here's an example:

{% raw %}
```yaml
types:
  - name: my_type
    title: "{{ my_fancy_type_title_lookup_function() }}"
```
{% endraw %}

{% raw %}
{: .note}
Every string is rendered, but only a string that starts with `"{{"` (or
`"{%"`) and ends with `"}}"` (or `"%}"`) can result in a non-string data
type; everything else (like `"https://example.com/{{ name }}"`) stays a
string, also several expressions in a row (`"{{ a }}{{ b }}"`). You will later see j2-string that do not have this
format and are used plainly (like `yac_if: new.data.blub|default('') == 'hi'`).
This is due to the fact, that some j2-strings should not be parsed when the
specs section is loaded but (sometimes even multiple times) at runtime.
{% endraw %}

## Builtins

Within j2-strings, you can use all
[builtin](https://jinja.palletsprojects.com/en/stable/templates) `functions`,
`tests` and `filters`.

### YAC Extensions

YAC provides some builtin functionality that extends the jinja2 defaults. You
will find them in the respective [Plugin](../plugins.md) source directory, where
you can also add your own extensions.

Inside [`types[].limits[]`](file/types/limits.md) the entity variables have a

scanned** and `new` is the **incoming entity** being created or changed.

### Keyword `omit`

The keyword `omit` is another YAC extension which will cause the
key, of which it is the value, to be removed completely.

{: .note}
The variable is defined everywhere, but the key is only removed for keywords
directly in a subschema of the [`schema`](file/schema.md) (so not inside of
`vays_options` or lists, and not for a whole property), for
`types[].links[].url` and for the per-entry keys in `types[].logs[].details`.
Anywhere else, the key stays (with an internal marker string as its value).

#### Example

{% raw %}
```yaml
user:
  name: "{{ user.full_name }}"
  age: "{{ omit }}"
```
{% endraw %}

This results in something like:

```yaml
user:
  name: Peter Platz
```

### Variable `context`

The variable `context` is an `object` and contains the unmodified content of the
according specs [section](file/context.md).

### Variable `loc`

This contains a string that represents the location of the j2-string being
rendered (including its own key) relative to the parsed root in the specs
(= each column in the table). The root is represented as `#`. (For example:
`#/properties/system_type/default`; for links it is
`#/types/{type}/links/{link}/url`.) In the plain j2-strings evaluated at
runtime (`yac_if`, `roles`, `sets`, `types[].limits[]`,
`types[].name_generator`) and in `repo.details` it is always `#`.

### Variable `env`

Is an `object` that contains all custom environment variables provided to the
application. For example the env variable `YAC_ENV__MY_CUSTOM_VAR="hello World"`
is available as `env.my_custom_var` with the value `hello World` in j2-strings.
This is mainly meant for secrets or configuration you don't want to put into the
specs file but rather inject them at runtime.

### Variable `request`

This contains data about the current request. `request.ip` is the remote IP and
`request.headers` is a dictionary of custom headers defined in the spec section
[request](./file/request.md).

### Variable `user`

Contains some details about the user making the current request.

The key `perms` contains the permissions the user has for the current operation,
rendered from the `roles` and `sets`.

{: .note}
The data in `user.token` is not standardized and just reflects what the Open ID
Connect identity provider sends within the token.

### Variable `operation`

Defines the operation the current request is doing, which can be one of:
`read`, `create`, `edit`, `delete` or `arbitrary` (which means only an action
is being executed)

### Variable `actions`

The list of actions that are requested to be executed alongside the current
request. (For `operation == "arbitrary"` this is actually the only thing done.)

{: .important}
This list may be incomplete due to actions defined with the `force` attribute
(which will add them implicitly if not provided).

### Variable `type`

The type of the entity that the current request refers to.

### Variable `old`

Contains the `name` and `data` of the already existing entity in the repository
the current request is referring to.

### Variable `new`

This is very similar to `old` but contains the `name` and `data` of a request
to create/edit that entity. So `new.name` may be a non-existing entity and
`new.data` contains unverified data that not yet is stored in the repository.

(`new.data` is actually what will be validated with the schema after generating
the schema.)

### Variable `name`

This is the same as `old.name` or `new.name` depending on the context. This
should usually be a good default to use but note the following special cases:

  - If an entity is being renamed, it contains the new name!
  - If an entity is being copied or linked, it contains the new name!

In [roles](file/roles.md) and [sets](file/sets.md), a rename, copy or link is
evaluated **twice**, because two entities are involved: once for the stored
source entity on its own (`name` and `old.name` are the name of the source,
`new.name` is unset) and once for the request as a whole (`name` is the new
name, as described above). See
[Permissions](perms.md#rename-copy-and-link-two-entities) for which
permission is taken from which evaluation.

### *Plugins*

`j2_*` plugins are the YAC-builtin and custom functions, filters and tests (see
[YAC Extensions](#yac-extensions) and [Plugins](../plugins.md)). They are
unavailable in the `repo` and `auth` sections because those are rendered at
process startup with a minimal Jinja2 environment; `repo.details` is rendered
per-call inside the repo plugin and therefore has full access to them.

### *Plugin specific* variables

Plugins may add specific variables. Check the respective [Plugin](../plugins.md)
for details.
